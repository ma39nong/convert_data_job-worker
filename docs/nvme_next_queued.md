# 正式排队数据：NVMe 单包或连续两包串行试验

这是一次真实队列的串行试验，不是同包ABBA对照。默认只处理一包；`--jobs 2` 连续处理两包，始终每次只启动一个转换子进程。只将本次临时工作区放到NVMe，读取原始/data输入，完整验证后发布到原本对应的正式输出并更新正式队列。成功来源在服务恢复后不重复转换。正式配置中的work_root、路由、批次、优先级、数据规则和状态指纹均不改写。

## 运行边界

- 必须在服务器本机，用现有接收器虚拟环境运行。脚本按队列中已登记的稳定来源、优先级及排队顺序选一条；当前候选只是预览，接管时会重新选择。
- 只有`--run`才开始接管。若当前包正在输入检查，先等待其进入正常处理阶段（或该检查自然失败），再请求维护和SIGTERM，确保已经在检查的当前包有机会完整处理完成，不因试验提前被放回队列。NVMe挂载、可写性、空间、服务状态、稳定来源和维护请求先检查。
- 若旧ABBA协调器仍运行，只向当前用户运行的那个精确脚本进程发送一次SIGINT，等待其当前试验包完成后退出，跳过剩余轮次。不会向子进程或服务发送SIGKILL。
- 仅允许接管事先记录的旧试验维护请求；其他操作者的维护请求保持不动并拒绝执行。新请求会阻止旧协调器擅自恢复服务。
- 使用sudo只请求正式服务正常退出及最后重新启动，处理数据仍以原用户运行。不通过`systemctl stop`的超时机制强杀当前作业，等待SIGTERM后的正常退出，必须确认inactive且Result=success。
- 服务释放正式worker.lock后，单包消费者才在同一个持久化状态目录取得该锁。旧试验协调锁也必须取得；因此不会与正式服务或旧对照试验并发处理。

## 处理流程

复制当前相同的源码、配置和消息定义到独立NVMe工程，子进程从该工程导入代码。使用原生校验后的正式配置字典，保留实际源、契约、schema、输出和指纹，只在子进程内改变work_root到新工程outputs。这样继续遵守job输出目录与清理所有权规则。

下一条候选必须满足持久化稳定观察次数/时长、原生快照签名一致和重试期限；源变更的候选不冒充稳定输入。随后新执行全部输入体检，创建进程内来源凭据，调用正式worker.process，保留原有清洗、30Hz对齐、来源/深度/触觉校验、完整视频解码、最终源哈希和发布复制/追加检查。质量排除和错误沿用正式队列规则。

测试成功即在正式队列中published、正式路由批次中正常追加，而非仅产生一份孤立测试数据。失败不会把未验证结果标为成功；恢复服务后沿用正式重试、排除及去重行为。

## 结果与恢复

报告、选中来源、源码哈希和日志位于`code/experiments/nvme-next-时间-标识/`。summary.json给出total_s和input_check、cleaning、conversion、output_verification、final_source_hash、archiving、publication、cleanup、other的互斥阶段耗时。本单包处理计时不包含此前队列等待、旧试验收尾、服务正常退出等待及源码复制。

单包完成或普通异常后，脚本只恢复自己仍持有的维护请求，并重启正常退出的服务。若服务异常退出或恢复失败，会保留报告供处理，不通过强制启动掩盖问题。若外部改变维护请求，保留其状态；服务可启动但仍按新的维护状态等待。SIGINT/SIGTERM只取消尚未启动的单包，已启动的本次处理会等它安全结束。

整个脚本需要保持终端运行；强制SIGKILL、断电或主机故障无法保证执行finally恢复，此时先确认单包进程已退出，再检查maintenance、worker.lock和systemd状态后恢复。

## 已验证范围

本地合成Sharpa/Wuji真实CDR/SQLite包验证正常正式发布、源最终核验失败阻止发布、服务仍active时拒绝打开队列、优先级/快照变化筛选、恢复后来源不重复。另用真正的克隆工程subprocess验证保留原正式指纹、修改临时work_root后，原队列恰好发布一包，另一包保持排队。子进程测试仅替代systemctl状态返回，不是服务器性能结果。正式服务生命周期需要服务器本机执行验证。


## 连续两条（`--jobs 2`）

服务正常退出后，在同一维护窗口内顺序启动两个单包消费者，每条都重新按当前持久队列顺序选择下一条稳定输入。第一条已published会从候选集中排除；第二条使用独立报告目录，沿用同一正式状态和NVMe工作区所有权指纹。两条之间不启动正式服务，也不运行原盘对照；全部结束后恢复原服务。

`runs/01/`、`runs/02/` 分别保存selected.json、result.json和run.log；总summary.json保存逐条results、processed_jobs、published_jobs、总处理时间和均值。质量排除沿用原规则并记录，不放宽条件为凑足两条成功结果。第一条若发生程序或来源一致性错误，保留真实队列的失败/重试状态，不继续启动第二条，恢复服务按正常规则处理；第二条失败不会回滚已发布第一条。

取消请求会让当前条安全结束后停止启动下一条，报告保留已完成条目。测试期间没有更改默认配置，完成后仍恢复原/data工作区的正式后台服务。测试只为验证连续处理的实际耗时及稳定性，不等于长期切换已完成。
