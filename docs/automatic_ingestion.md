# 自动接收、清洗和追加数据集

本功能先在本地准备和验证。项目不会自动连接数据服务器、上传代码或安装服务。服务单元和服务器配置均为待编辑的模板。

## 输入和输出

以配置的 `data_root` 为公共前缀：

| 路由 | 只读输入 | 持续追加的 LeRobot v2.1 输出 |
| --- | --- | --- |
| Sharpa A | `origin-data/sharpa/A/episodeXX` | `clean-data-lerobot/sharpa/A` |
| Sharpa B | `origin-data/sharpa/B/episodeXX` | `clean-data-lerobot/sharpa/B` |
| Wuji A | `origin-data/wuji/A/episodeXX` | `clean-data-lerobot/wuji/A` |
| Wuji B | `origin-data/wuji/B/episodeXX` | `clean-data-lerobot/wuji/B` |

四条路由独立建索引和去重，同名 `episodeXX` 可以分别存在于不同路由。输出的 `episode_000000` 等索引是数据集内部编号，不能直接当作原始包序号；原始目录、采集标识、文件哈希和处理记录保存在来源记录中。

Sharpa 保留三路 RGB、头部 uint16 深度、双手十指的形变图和六维力/力矩，以及状态/动作和审计字段；Wuji 保留三路 RGB、深度、状态/动作和审计字段。沿用主链路的裁剪规则、独立静止覆盖检查、30 Hz 对齐及独立来源校验。

## 上传端发布协议

上传器先在 `.uploading/<任务编号>/` 写入完整包，完成传输检查、关闭全部文件后，将**整个包目录**一次性重命名为正式分类目录下的 `episodeXX`。进入正式目录是主要的上传完成依据，不增加人工完成标记或回调。

上游必须满足：

- 临时目录和目标 A/B 目录位于同一个可执行原子重命名的文件系统/挂载范围。操作必须使用 `rename(2)` 等同等语义；遇到 `EXDEV` 应中止发布并调整临时区位置，禁止自动退化为复制再删除。
- 整目录一次发布，不能先建立正式 episode 再逐文件复制。已有同名目录不能被覆盖；任务编号和目标 episode 应唯一，发布后不再写入。
- 仅路径接近不能证明同一文件系统。可通过下面的只读预检比较设备号；设备号相同是必要条件，绑定挂载等边界下仍可能无法重命名。上传器必须处理实际重命名失败，且不能触发复制回退。

```bash
ingest-worker check-upload-layout --config configs/ingest.local.yaml \
  --staging /your/data-root/.uploading/task-id --route sharpa-A
```

预检要求两个目录已经存在，不移动文件、不修改输入。它检查路径和设备号，输出 `uploader_operation_verified: false`，**不能证明外部上传器已经采用指定操作**。本项目不包含上传器源码；当前将该行为作为上游对接约定，本地演练使用实际同文件系统目录重命名验证接收侧。

接收器只枚举配置推导出的四个正式 A/B 目录的直接子目录，匹配 `episode` 加数字；不扫描整个 `data_root`，不递归发现包，也不进入 `.uploading/`。即便正式目录内存在 `.uploading/`，其内容也被忽略。正式输入根目录不能解析到 `.uploading/` 下。

## 首次启动与历史范围

配置必须显式设置 `initial_history`，也可在单条 route 内覆盖：

```yaml
# 默认模板：首次成功扫描时已有的包均跳过，之后出现的包自动接收。
initial_history: {mode: none}
routes:
  - robot: sharpa
    group: A
    initial_history:
      mode: include
      episodes: [episode12, episode18]
  - {robot: sharpa, group: B}
  - {robot: wuji, group: A}
  - {robot: wuji, group: B}
```

`include` 只选择首次扫描时列出的历史包；同一次扫描发现的其他历史包跳过。`all` 表示明确允许全部历史包。未来到达的包不受初始清单限制，清单内尚未到达的包也会在出现时发现。

每条路由在**第一次成功枚举正式目录时**，将策略和跳过的精确目录名原子写入队列数据库。目录缺失或不可访问时不提前建立空基线；这是一个首次扫描快照，不是按 mtime 或 episode 编号推测历史。服务尚未首次扫描时已发布的包都属于该快照；需要处理它们，应预先选入清单或选择 `all`。

重启沿用该基线和原有队列，补查停机期间新出现的包，不重新划分历史，也不因下一条尚未出现而漏掉最后一条。跳过项在 `status` 和 `status.json` 的 `initial_history` 中可查。已经初始化的策略不能通过修改配置静默改变；该路由会报错，需恢复原策略。新增历史回补应作为单独受控批次安排，不删除队列来触发回补。

从 `27811d8` 升级时保留原队列和发布版本；已登记任务继续恢复，新的初始策略只作用于尚未登记的已有目录。该策略不改变转换配置指纹，不触发重新转换。首次启动前应审阅配置，避免误选 `all`。

## 防御检查与录制质量

上传发布与录制质量是两件事：原子进入正式目录表示上游承诺传输结束，不能保证录制质量合格。采集状态、清洗规则及质量阈值均沿用现有主链路。

1. 发现历史策略允许的、名称为 `episode` 加数字的真实目录，立即登记队列。无需下一条出现；空目录或缺 metadata 的异常发布同样登记并等待体检通过。
2. 递归记录文件集合、大小、mtime、ctime、inode/device 和目录项。文件仍在变化时重新开始观察；特殊文件和符号链接不进入处理。
3. 保留额外防御检查：默认每 10 秒扫描，至少 3 次独立扫描一致，并从首次一致状态起稳定至少 60 秒。短时间反复调用扫描不能凑够次数，重启会保留观察记录。这不是主要的上传完成依据。
4. 新目录出现时优先检查其紧邻的上一条；这只调整检查顺序，不能跳过稳定观察或完整性检查。最后一条仍依靠同一后台扫描机制自动处理，不需要下一条出现。
5. 对稳定目录执行结构体检：采集状态有效、metadata 所列分卷齐全、SQLite `quick_check` 通过、总消息数和各话题消息数匹配、必需流存在且可读、关节/消息契约正确、图像端点编码和形状有效。分卷不能越出包目录；未传完的临时文件/WAL/SHM 会阻止处理。
6. 计算输入文件 SHA-256，复查目录快照。体检失败沿用现有 `waiting_upload` 状态名等待重试；这个状态表示尚未通过接收体检，不否定上游已经发布，也不把采集失败误判为传输未结束。输入有新变化时重新观察稳定，不消耗转换重试次数。

**协议异常：** 如果上传端绕过临时区、跨盘复制或正式发布后继续写入，便不符合上述约定；稳定扫描不能替代原子发布，也不能预知未来写入。接收侧仍通过冻结副本和源变化检查防御异常。`collection_state.json` 是现有采集契约的一部分，不是上传完成标记。

## 暂存、变化检测和发布

- 结构体检后，逐文件建立独立暂存副本，并核对暂存内容与已验证输入的哈希。原始包不改名、不移动、不删除。
- 复制使用只读、禁止跟随符号链接的文件打开方式；暂存前后复查输入。清洗和转换只读取冻结的暂存副本。
- 处理期间持续监测原始目录。转换后再次执行完整输入检查，发布入口切换前也复查变化。只要观察到输入变化，本次尝试不发布，清理本次暂存，重新等待稳定。
- 每个输入必须通过独立清洗覆盖检查、来源逐项校验及视频/数据校验。重写数据集索引后，新追加片段再次校验。
- 已验证结果在隐藏的版本目录中完整构建；旧数据文件通过只读硬链接继承，元数据另存。最后原子替换 A/B 的符号链接入口，避免让读取方看到构建到一半的新版本。
- 未变化的已发布内容不重新转换。队列落盘前进程退出，但入口已经切换时，重启会从已发布版本对账，不重复追加。
- 原始包进入正式目录后、本次转换结果发布前若变化，丢弃本次结果并重新等待体检；数据集发布后同名原始包再变化则记录 `conflict`，保留已发布结果，不自动覆盖历史训练数据。两种情况都属于上游发布约定异常，日志保留原因；后者需单独评估，不能默默重新追加。

发布目录在文件系统上是符号链接，进入后仍是标准 `data/`、`videos/`、`meta/` 和审计记录。长期读取应先固定到某个完整版本：

```bash
DATASET=$(readlink -f /your/data-root/clean-data-lerobot/sharpa/A)
# 将 "$DATASET" 作为 loader 的 root 或上传路径。
```

上传工具应跟随入口或上传其解析后的目录，不要只上传符号链接文件。历史版本暂不自动回收，避免破坏已经固定到旧版本的读取任务；数据文件继承使用硬链接，但元数据和目录项仍会增长，正式部署前需确定版本保留和空间监控策略。

## 本地配置与命令

```bash
pip install -e '.[conversion,test]'

# 只校验配置和四条映射，不创建目录或开始处理。
ingest-worker check-config --config configs/ingest.local.yaml

# 扫描一轮：首次通常只是登记和观察，不代表马上开始处理。
ingest-worker once --config configs/ingest.local.yaml

# 持续运行；仅访问配置指定的本地目录。
ingest-worker run --config configs/ingest.local.yaml

# 从持久化队列读取当前状态，也可查看进程 stdout 日志。
ingest-worker status --config configs/ingest.local.yaml
```

未重新安装 CLI 入口时，可用 `python -m convest.ingest.cli` 替代 `ingest-worker`。

本地模板的公共前缀为项目内 `outputs/ingest-local/data`，不会访问桌面挂载的数据服务器。输入目录由上传方创建；不存在时在状态中记录路由错误，后续扫描会重试。

服务器模板 [ingest.server.example.yaml](../configs/ingest.server.example.yaml) 中的 `data_root` 必须在正式部署前替换为**服务器本机路径**，不能照搬工作站上的 SSHFS 挂载路径。模板 [ingest-worker.service.example](../deploy/ingest-worker.service.example) 仅供后续安装参考，本阶段不安装、不启用。

| 字段 | 默认值 | 含义 |
| --- | --- | --- |
| `poll_seconds` | 10 | 扫描间隔；处理结束后再进行下一轮 |
| `stable_scans` | 3 | 文件快照一致的独立扫描次数，至少 2 |
| `stable_seconds` | 60 | 当前一致快照持续的最短观察时间 |
| `max_checks_per_scan` | 4 | 每轮最多执行几个较重的结构体检 |
| `max_jobs_per_scan` | 1 | 每轮最多冻结/清洗/转换几个包，限制暂存占用和扫描延迟 |
| `retry_seconds` | 60 | 未就绪检查间隔；转换重试使用有上限的指数退避 |
| `max_attempts` | 3 | 同一未变化输入的转换/发布尝试次数 |
| `initial_history` | 必须显式配置；模板为 `none` | 首次成功扫描的历史范围，支持 `none` / `include` / `all`；route 可覆盖 |
| `state_root` | 项目内状态目录 | SQLite 队列、观察记录、轻量报告和错误原因 |
| `work_root` | 项目 `outputs/` 下 | 有所有权标识的临时工作目录 |

60 秒仅为额外防御观察参数，上传结束依据仍是上游按约定原子发布到正式目录。重试前仍检查输入；文件变化会重置稳定计数。资源不足、程序/发布错误会自动重试，达到上限记为 `failed`；数据连续性不符合主链路要求记为 `excluded`，不反复消耗资源。其余包继续处理。

工作区和输出区不能与输入重叠。已存在的非空、非本服务拥有的输出目录不会被接管；空输出目录可以安全初始化。只有本服务拥有的暂存目录会自动清理。暂存和输出空间不足时拒绝开始新尝试。

## 状态和验收

常见状态：`waiting_stable`、`waiting_upload`、`checking`、`staging`、`processing`、`published`、`retry`、`failed`、`excluded`、`conflict`。

- `state_root/queue.sqlite3`：队列和稳定观察，使用持久化事务；同一状态目录只允许一个消费者。
- 每套输出还持有独立发布锁；即便误用两个不同的队列目录，也不能同时向同一套数据集追加。
- `state_root/status.json`：最近一轮扫描汇总。CLI `status` 读取数据库，可看到正在进行的任务。
- `state_root/attempts/`：轻量处理、排除和错误报告；原始副本和清洗中间包在本次尝试结束后清理。
- 数据集 `ingest/generation.json`：当前完整版本、父版本及配置指纹。
- 数据集 `ingest/sources/`：来源独立验证和裁剪报告。
- 数据集 `conversion/records/`：输入文件哈希、就绪依据、稳定观察记录、暂存源、数据索引和已发布文件哈希。

增量发布检查新增加的完整数据，对旧的只读硬链接校验文件属性并继承原有验证结果；它不是每次都重新解码全部历史数据。需要全量复验时，可对固定版本运行主链路的 `convert-worker verify`。不要修改版本目录中的训练文件；发现旧文件属性变化时会拒绝追加。

本地测试使用真实编码的合成 ROS2 SQLite/CDR 包，覆盖临时上传目录忽略、整目录重命名后立即登记、最后一条自动处理、首次历史范围持久化和升级恢复，以及四路分离追加、半包、连续扫描次数、分卷/SQLite/消息数/必需流、暂存与发布期间源变化、进程重启、队列提交中断、入口切换失败和去重。实际服务器权限、文件系统原子重命名/硬链接行为、上游发布约定及容量策略需要在获准部署后联调。

可在开发环境复现四路端到端演练：

```bash
python scripts/demo_ingest_local.py
```

脚本仅在项目 `outputs/ingest-demo-*` 内生成合成输入，经 `.uploading/` 到正式目录的实际重命名发布，调用实际 CLI 完成清洗、转换和追加，检查原始文件哈希不变、重复扫描不重复追加、暂存已清理及四套输出均通过校验。最终打印 `validation.json` 路径。演练为缩短等待使用 2 次扫描/1 秒；正式模板仍采用 3 次扫描/60 秒。演练需要项目测试依赖，不会连接服务器。
