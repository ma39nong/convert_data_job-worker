# 自动接收、清洗和追加数据集

本功能先在本地准备和验证。项目不会自动连接数据服务器、上传代码或安装服务。服务单元和服务器配置均为待编辑的模板。

## 输入和输出

以配置的 `data_root` 为公共前缀：

| 路由 | 只读输入 | LeRobot v2.1 批次父目录 |
| --- | --- | --- |
| Sharpa A | `origin-rosbag/sharpa/A/episodeXX` | `data-lerobot/sharpa/A/` |
| Sharpa B | `origin-rosbag/sharpa/B/episodeXX` | `data-lerobot/sharpa/B/` |
| Wuji A | `origin-rosbag/wuji/A/episodeXX` | `data-lerobot/wuji/A/` |
| Wuji B | `origin-rosbag/wuji/B/episodeXX` | `data-lerobot/wuji/B/` |

四条路由独立计时和去重，同名 `episodeXX` 可以分别存在于不同路由。A/B 是包含多个批次的父目录，不是单套数据集根目录；每个 `起始序号_结束序号_data_lerobot` 子目录才是一套标准数据集，内部含 `data/`、`videos/`、`meta/` 等。输出的 `episode_000000` 是批内编号，不能直接当作原始包序号；原始目录、采集标识、文件哈希和处理记录保存在来源记录中。

Sharpa 保留三路 RGB、头部 uint16 深度、双手十指的形变图和六维力/力矩，以及状态/动作和审计字段；Wuji 保留三路 RGB、深度、状态/动作和审计字段。沿用主链路的裁剪规则、独立静止覆盖检查、30 Hz 对齐及独立来源校验。

## 72 小时分批与命名

`batch_hours: 72` 按各路由的墙上时间独立计时，以本批第一个原始包完成“检查、清洗、转换、校验并成功追加”的时间为起点，不按目录日期或录制时长分组，也不从进程启动时计时。

- 到期前成功追加的包属于同一批。到期前已开始处理的包允许完成后归入该批，再进行封存；随后开始的包进入新批次。失败重试若在封存后才成功，则进入新的活动批，不重开旧批。
- 名称取**实际成功纳入的原始 episode 数字最小值和最大值**。例如纳入 `episode36`、`episode41`、`episode68`，名称为 `36_68_data_lerobot`。失败包、未就绪包和质量排除包不计入范围。范围允许缺号和与其他批次交叠，精确来源清单以批次记录为准。
- 活动批的名字随序号范围更新；不会每成功一个包就留下一套旧范围目录。封存后名字和内容固定。不同批若恰好需要同名目录，拒绝覆盖并报告冲突，不能静默合并。
- 到期时核对全部训练文件的 SHA-256，并执行整批数据/视频解码校验；只有通过后才记为 `sealed`。校验失败记录 `seal_error`，该路由暂停追加，后续扫描重试校验，其他路由继续处理。
- 后台扫描在没有新包时也会封存最后一批；服务停机期间的计时不重置，恢复后补做封存。不因空闲跨过多个周期而创建空批。每个新批次的内部 episode 索引从 0 开始。
- 已成功来源在本路由的所有批次间去重。历史来源即使再次被扫描，也不会追加到新批；源异常变化仍记为冲突并保留原结果。

批次状态、计时和实际来源清单保存在各 A/B 父目录的隐藏 `.ingest/batches.json`，封存校验摘要在 `.ingest/seals/`，CLI `status` 与扫描状态文件也展示这些信息。隐藏的内部版本目录用于中断恢复，不属于可交付批次。交付时选择 `state: sealed` 且封存校验通过的范围目录。

## 接收端职责与扫描范围

服务只读取配置输入目录里收到的 episode，不对接或修改上传器，不要求提供上传器源码、上传完成回调、人工标记、临时目录布局或指定移动方式。episode 可以整体出现，也可能在目录创建后逐步到达；接收侧统一通过可观测数据检查是否允许处理。

接收器只枚举配置推导出的四个 A/B 输入目录的直接子目录，匹配 `episode` 加数字；不扫描整个 `data_root`，不递归发现包。输入根目录之外的数据不会进入队列；即便分类目录内存在 `.uploading/` 等不匹配名称的目录，其内容也被忽略。这只是接收器的扫描范围，不是对上传方的要求。

## 首次启动与历史范围

配置必须显式设置 `initial_history`，也可在单条 route 内覆盖：

```yaml
# 服务器模板：已有包和未来新包都处理。本地模板为 none，可按需更改。
initial_history: {mode: all}
routes:
  - robot: sharpa
    group: A
    initial_history:
      mode: include
      episodes: [episode12, episode18]
  - {robot: sharpa, group: B}
  - {robot: wuji, group: A}
  - {robot: wuji, group: B}
```

`include` 只选择首次扫描时列出的历史包；同一次扫描发现的其他历史包跳过。`all` 表示明确允许全部历史包。未来到达的包不受初始清单限制，清单内尚未到达的包也会在出现时发现。

每条路由在**第一次成功枚举输入目录时**，将策略和跳过的精确目录名原子写入队列数据库。目录缺失或不可访问时不提前建立空基线；这是一个首次扫描快照，不是按 mtime 或 episode 编号推测历史。服务尚未首次扫描时已出现的包都属于该快照，包括尚未传完整的目录；需要处理它们，应预先选入清单或选择 `all`。

重启沿用该基线和原有队列，补查停机期间新出现的包，不重新划分历史，也不因下一条尚未出现而漏掉最后一条。跳过项在 `status` 和 `status.json` 的 `initial_history` 中可查。已经初始化的策略不能通过修改配置静默改变；该路由会报错，需恢复原策略。新增历史回补应作为单独受控批次安排，不删除队列来触发回补。

首次历史策略本身不改变转换指纹，已登记任务优先恢复。但本次分批布局与旧的单数据集布局不同，配置指纹和输出路径已经变更：模板使用新的 `*-batches` 状态/暂存目录，拒绝直接复用旧配置的所有权标识，不自动接管、移动或删除旧数据集。旧目录和旧批处理保持原样。新配置首次扫描按所选历史策略登记；服务器模板明确采用 `all`。不应手动删除队列来触发回补。

## 防御检查与录制质量

输入可处理性与录制质量分别检查：目录出现会触发登记，通过持续稳定观察及结构体检后才开始处理；后续仍须通过既有清洗、转换和数据集校验。采集状态、清洗规则及质量阈值均沿用现有主链路。

1. 发现历史策略允许的、名称为 `episode` 加数字的真实目录，立即登记队列。无需下一条出现；空目录或缺 metadata 的目录同样登记并等待体检通过。
2. 递归记录文件集合、大小、mtime、ctime、inode/device 和目录项。文件仍在变化时重新开始观察；特殊文件和符号链接不进入处理。
3. 默认每 10 秒扫描，至少 3 次独立扫描一致，并从首次一致状态起稳定至少 60 秒。短时间反复调用扫描不能凑够次数，重启会保留观察记录。稳定观察只是接收检查的一部分，不能替代结构体检。
4. 新目录出现时优先检查其紧邻的上一条；这只调整检查顺序，不能跳过稳定观察或完整性检查。最后一条仍依靠同一后台扫描机制自动处理，不需要下一条出现。
5. 对稳定目录执行结构体检：采集状态有效、metadata 所列分卷齐全、SQLite `quick_check` 通过、总消息数和各话题消息数匹配、必需流存在且可读、关节/消息契约正确、图像端点编码和形状有效。分卷不能越出包目录；未传完的临时文件/WAL/SHM 会阻止处理。
6. 计算输入文件 SHA-256，复查目录快照。体检失败沿用现有 `waiting_upload` 状态名等待重试；该状态表示尚未通过接收体检，不推断上传器正在做什么，具体原因见错误记录。输入有新变化时重新观察稳定，不消耗转换重试次数。

**判断边界：** 接收器只能判断当前观测到的数据是否稳定且结构完整，不能证明将来永远不会再写入。处理使用冻结副本，并在处理前后及数据集发布前持续检查源变化。`collection_state.json` 是既有归档/采集质量记录，不是新增的人工上传完成标记；其 `finalized` 状态也不能单独证明文件已传完整。

## 暂存、变化检测和发布

- 结构体检后，逐文件建立独立暂存副本，并核对暂存内容与已验证输入的哈希。原始包不改名、不移动、不删除。
- 复制使用只读、禁止跟随符号链接的文件打开方式；暂存前后复查输入。清洗和转换只读取冻结的暂存副本。
- 处理期间持续监测原始目录。转换后重新计算原始文件的全部 SHA-256 并复核快照，但不再次扫描 SQLite、统计消息或解析必需数据流；发布入口切换前也复查变化。只要观察到输入变化，本次尝试不发布，清理本次暂存，重新等待稳定。
- 每个输入必须通过独立清洗覆盖检查、来源逐项校验及视频/数据校验。重写数据集索引后，新追加片段再次校验。
- 已验证结果在当前批次的隐藏版本目录中完整构建；批内旧数据文件通过只读硬链接继承，元数据另存。最后原子切换批次的内部指针，并同步序号范围入口，避免让读取方看到构建到一半的数据。入口或批次清单更新中断时，下次扫描按已提交版本恢复名称和去重记录。
- 未变化的已发布内容不重新转换。队列落盘前进程退出，但入口已经切换时，重启会从已发布版本对账，不重复追加。
- 原始包在本次转换结果发布前若变化，丢弃本次结果并重新等待体检；数据集发布后同名原始包再变化则记录 `conflict`，保留已发布结果，不自动覆盖历史训练数据。日志保留原因；后者需单独评估，不能默默重新追加。

### 完整性检查复用与读盘范围

自动接收的一次处理尝试仅执行一次完整接收体检。复制过程中同步计算源字节的 SHA-256，并独立重新读取目的文件校验哈希，避免仅验证读入数据而遗漏目的写入错误。成功后创建只在当前进程内使用的工作副本凭据，绑定副本绝对路径、文件集合/属性、契约及消息定义内容和原始就绪报告。

job 使用该凭据复用结构检查结果和输入频率报告，避免对同一副本重新执行 `quick_check`、消息统计、整包预检哈希和必需流预解析。凭据不能从队列 JSON、文件或 CLI 导入；普通独立 job、重启恢复、下一次重试仍执行自己的完整预检。工作副本在使用凭据前、处理完成后及最终提交前均核对强属性快照；契约或副本变化会阻止提交。

这是检查复用，不是取消源内容核验：仍保留首次源哈希、复制时源字节哈希、目的副本独立读回哈希、处理完成的副本哈希，以及发布前原始包全量哈希。源前后内容一致时不必重复解码结构检查。清洗规则、连续性阈值、来源对齐审计、完整视频解码、深度和触觉逐行对比、发布副本哈希及追加校验不变。整包没有有效示教动作的筛查是独立问题，本优化不新增动作阈值或任务阶段识别。

本实现减少一次工作副本预检和一次原始包重复结构解析，但仍有必要的全量读写，不承诺固定提速倍数；耗时也受存储、缓存和其他作业影响。

A/B 下的范围目录在文件系统上是符号链接，进入后仍是标准 `data/`、`videos/`、`meta/` 和审计记录。A/B 父目录本身是普通目录。训练、校验或交付应选择一个具体批次；长期读取活动批时先固定到某个完整版本：

```bash
DATASET=$(readlink -f /your/data-root/data-lerobot/sharpa/A/36_68_data_lerobot)
# 将 "$DATASET" 作为 loader 的 root 或上传路径。
```

交付工具应跟随入口或上传其解析后的目录，不要只上传符号链接文件，也不要把 A/B 父目录当作一套数据集。历史内部版本暂不自动回收，避免破坏已经固定到旧版本的读取任务；批内数据文件继承使用硬链接，但元数据和目录项仍会增长。正式部署前需确定版本保留和空间监控策略。

## 本地配置与命令

```bash
pip install -e '.[conversion,test]'

# 只校验配置和四条映射，不创建目录或开始处理。
ingest-worker check-config --config configs/ingest.local.yaml

# 扫描一轮：首次通常只是登记和观察，不代表马上开始处理。
ingest-worker once --config configs/ingest.local.yaml

# 持续运行；仅访问配置指定的本地目录。
ingest-worker run --config configs/ingest.local.yaml

# 从持久化队列读取当前状态，也可查看进程 stdout 日志。
ingest-worker status --config configs/ingest.local.yaml

# 请求维护：完成当前包的发布及清理，不再开始下一包。
ingest-worker drain --config configs/ingest.local.yaml

# 维护结束后恢复接收；沿用队列和批次，不重新追加成功包。
ingest-worker resume --config configs/ingest.local.yaml
```

未重新安装 CLI 入口时，可用 `python -m convest.ingest.cli` 替代 `ingest-worker`。

需要临时前移已登记的某种机器人数据时，可在服务本机运行 `python scripts/prioritize_ingest.py --config configs/ingest.server.yaml --robot sharpa` 预览，再加 `--apply` 执行。工具先只读筛选，再用一条原子更新语句前移现有待处理项；文件检查不占用数据库写锁，提交时重新排除已经开始处理的包。写锁繁忙时最多等待重试 10 分钟，定期打印等待信息，超时不更改排序。不改作业状态、稳定性记录或输出，不打断当前包，下一轮调度生效。此操作只针对当时的队列，不设置永久的机器人优先级，后续新到达的数据仍使用正常调度规则。禁止通过 SSHFS 写入运行中的队列数据库。

本地模板的公共前缀为项目内 `outputs/ingest-local/data`，不会访问桌面挂载的数据服务器。输入目录由上传方创建；不存在时在状态中记录路由错误，后续扫描会重试。

服务器模板 [ingest.server.example.yaml](../configs/ingest.server.example.yaml) 中的 `data_root` 必须在正式部署前替换为**服务器本机路径**，不能照搬工作站上的 SSHFS 挂载路径。模板 [ingest-worker.service.example](../deploy/ingest-worker.service.example) 仅供后续安装参考，本阶段不安装、不启用。

| 字段 | 默认值 | 含义 |
| --- | --- | --- |
| `poll_seconds` | 10 | 扫描间隔；处理结束后再进行下一轮 |
| `stable_scans` | 3 | 文件快照一致的独立扫描次数，至少 2 |
| `stable_seconds` | 60 | 当前一致快照持续的最短观察时间 |
| `max_checks_per_scan` | 4 | 每轮最多执行几个较重的结构体检 |
| `max_jobs_per_scan` | 1 | 每轮最多冻结/清洗/转换几个包，限制暂存占用和扫描延迟 |
| `retry_seconds` | 60 | 未就绪检查间隔；转换重试使用有上限的指数退避 |
| `max_attempts` | 3 | 同一未变化输入的转换/发布尝试次数 |
| `batch_hours` | 72 | 每条路由每批持续时间，从首个成功追加起计时；正整数小时 |
| `initial_history` | 必须显式配置；服务器模板 `all`，本地模板 `none` | 首次成功扫描的历史范围，支持 `none` / `include` / `all`；route 可覆盖 |
| `state_root` | 项目内状态目录 | SQLite 队列、观察记录、轻量报告和错误原因 |
| `work_root` | 项目 `outputs/` 下 | 有所有权标识的临时工作目录 |

60 秒是接收侧可调整的稳定观察参数，不是“等待后必然完整”的承诺；还必须通过归档状态、metadata、分卷、SQLite、消息数量及必需流检查。重试前仍检查输入；文件变化会重置稳定计数。资源不足、程序/发布错误会自动重试，达到上限记为 `failed`；数据连续性不符合主链路要求记为 `excluded`，不反复消耗资源。其余包继续处理。

工作区和输出区不能与输入重叠。已存在的非空、非本服务拥有的输出目录不会被接管；空输出目录可以安全初始化。只有本服务拥有的暂存目录会自动清理。暂存和输出空间不足时拒绝开始新尝试。

## 状态和验收

常见状态：`waiting_stable`、`waiting_upload`、`checking`、`staging`、`processing`、`published`、`retry`、`failed`、`excluded`、`conflict`。

- `state_root/queue.sqlite3`：队列和稳定观察，使用持久化事务；同一状态目录只允许一个消费者。
- 每套输出还持有独立发布锁；即便误用两个不同的队列目录，也不能同时向同一套数据集追加。
- `state_root/status.json`：最近一轮扫描汇总。CLI `status` 读取数据库，可看到正在进行的任务。
- `state_root/progress.json`：当前/最近一次处理的细分阶段、阶段起点和最近更新时间；大文件复制和哈希约每 5 秒报告已处理字节。SQLite 检查等不可分步操作只报告阶段起点，不能把缺少字节更新当作进程心跳或卡死证明。输出发布与清理分别记录；job 的 `completed` 不代表外层已经 `published`。
- A/B 父目录 `.ingest/batches.json`：活动/封存批次、计时、序号范围及实际纳入清单；`.ingest/seals/`：整批校验摘要。CLI `status` 同时读取各路由批次状态。
- `state_root/attempts/`：轻量处理、排除和错误报告；原始副本和清洗中间包在本次尝试结束后清理。
- 数据集 `ingest/generation.json`：当前完整版本、父版本及配置指纹。
- 数据集 `ingest/sources/`：来源独立验证和裁剪报告。
- 数据集 `conversion/records/`：输入文件哈希、就绪依据、稳定观察记录、暂存源、数据索引和已发布文件哈希。

增量发布检查新增加的完整数据，对本批旧的只读硬链接校验文件属性并继承原有验证结果；每批封存时再执行完整 SHA-256 和整批解码校验。该校验使用独立元数据副本，避免写入当前可读版本；临时校验目录随后清理。需要手动全量复验时，可对固定批次版本运行主链路的 `convert-worker verify`。不要修改版本目录中的训练文件；发现旧文件属性变化时会拒绝追加或封存。

### 维护和安全更新

`drain` 写入持久化维护请求，不杀进程、不删除队列、不改变配置指纹。处理中的包继续完成来源复核、发布及暂存清理；处于首次完整体检时等待该体检返回，但不再启动复制/转换。每次选择下一包前都检查维护请求，支持一轮处理预算大于 1 的情况。服务继续存活；只有 `status` 的 `last_scan.maintenance` 为 `drained` 后才达到维护边界，此时停止服务再更新代码。维护期间不扫描输入和封存批次，恢复后补查新包和到期批次。

维护请求跨重启保留；完成更新后必须显式 `resume` 才继续处理。若进程在作业中异常退出，恢复和重试仍沿用原有规则。SIGTERM 也会阻止继续启动下一包，但不能代替维护状态确认；不要用强制终止或直接覆盖正在运行的 Python 源文件来更新服务。

这些命令需要运行中的版本支持。旧版本第一次升级可使用 `deploy/upgrade_server.sh`，先向旧服务发送 SIGTERM，等待它正常完成当前扫描并退出，再替换经过校验的源码；不使用带超时强杀的停服方式。升级过程保留环境、实际配置、队列、批次和原始数据。脚本及发布包必须先放在运行工程之外，不能提前覆盖运行中的模块。

本地测试使用真实编码的合成 ROS2 SQLite/CDR 包，覆盖扫描范围外目录忽略、直接复制或整目录移动后自动登记、最后一条自动处理、首次历史范围持久化和升级恢复，以及四路分离追加、半包、连续扫描次数、分卷/SQLite/消息数/必需流、暂存与发布期间源变化、进程重启、队列提交中断、入口切换失败和去重。实际服务器权限、输出文件系统的原子切换/硬链接行为及容量策略需要在获准部署后联调；这些是输出数据集发布要求，不是上传器协议。

可在开发环境复现四路端到端演练：

```bash
python scripts/demo_ingest_local.py
```

脚本仅在项目 `outputs/ingest-demo-*` 内生成合成输入，模拟输入目录里先出现不完整 episode、随后文件补齐，调用实际 CLI 完成清洗、转换和追加，检查半包不会处理、原始文件哈希不变、重复扫描不重复追加、暂存已清理及四套输出均通过校验；通过传入模拟到期时刻验证全部四批完整校验和封存，无需实际等待 72 小时。最终打印 `validation.json` 路径。演练为缩短稳定观察使用 2 次扫描/1 秒；正式模板仍采用 3 次扫描/60 秒。演练需要项目测试依赖，不会连接服务器或对接上传器。
